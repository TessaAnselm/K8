Foundation

What Is Kubernetes & Why Is It Attacked?

Kubernetes (K8s) is an open-source system for automating deployment, scaling, and management of containerized applications. Google open-sourced it in 2014. Today it runs most major companies' infrastructure making it the highest-value target in cloud security.

The Restaurant Analogy

Think of Kubernetes like a restaurant.
The dining room (your apps) is public — customers come in, eat, leave.
The kitchen + manager's office (the K8s control plane) should never be public.
But misconfigured clusters accidentally put the manager's office on the street with the door unlocked.

What Attackers Target
API Server (port 6443) — the brain, controls everything
etcd (port 2379) — raw database, contains all secrets
kubelet (port 10250) — manages each node directly
Service accounts — identity tokens pods use to call the API
Root Causes

The 3 Buckets And Why They Overlap

Most attacks chain multiple root causes. Remove any one layer and the attack often breaks.

⚙️
53%
Misconfiguration

Human error — exposed API server, over-permissioned service accounts, missing Pod Security Admission. K8s did what it was told. The fix is policy enforcement and automation, not a patch.

🐛
38%
Code Bugs (CVEs)

Software flaws regardless of configuration — memory bugs, logic errors, input validation failures. You can configure perfectly and still be vulnerable. The fix is patching K8s, runc, the kernel, ingress controllers.

📦
9%
Supply Chain

Something you pulled in is already compromised — a base image with CVEs, a poisoned PyPI package like LiteLLM 1.82.7. The fix is scanning, signing, and pinning all dependency versions.

How They Chain Together
# Real attack pattern — none of these work alone Malicious PyPI package installed ← Supply Chain + Kubernetes SA token auto-mounted ← Misconfiguration + Token has cluster-wide secret access ← Misconfiguration + No network policy blocking egress ← Misconfiguration = Full cluster compromise + exfiltration

Supply Chain Critical March 24, 2026 ★ Featured Case Study

LiteLLM, Trivy, and TeamPCP: The 3 Hop Supply Chain Attack

TeamPCP compromised Trivy, a tool used across thousands of CI CD pipelines, then used stolen publishing credentials to poison LiteLLM, an AI gateway downloaded over 3.4 million times daily. The malicious versions deployed a Kubernetes cluster takeover payload, impacting multiple layers of the software supply chain. This attack spans all three root cause categories and maps to more than eight MITRE ATT and CK techniques.

The Attack Chain
01
Trivy CI/CD Compromised — CVE-2026-33634 (CVSS 9.4)
TeamPCP exploited a misconfigured pull_request_target workflow in Trivy's GitHub CI to exfiltrate Aqua Security's PyPI publish token. Security scanners are uniquely dangerous — they have broad read access to environment variables and runner memory by design.
T1078 — Valid AccountsT1552 — Unsecured Creds
02
Checkmarx KICS Also Compromised
Using stolen credentials, TeamPCP pivoted to compromise KICS. Each compromised environment yielded credentials that unlocked the next target. Phase 08 of an ongoing campaign begun December 2025.
T1195 — Supply ChainT1078 — Valid Accounts
03
LiteLLM 1.82.7 + 1.82.8 Poisoned on PyPI
Malicious versions published directly to PyPI, bypassing GitHub release process. Version 1.82.8 used a .pth file — executed automatically on every Python interpreter startup. Live for ~40 minutes before quarantine.
T1195.001 — Compromise Software Supply ChainT1546 — Event Triggered Execution
04
3-Stage Payload Executes on Victim Systems
Once installed, the payload ran immediately — even during pip install itself. No user interaction beyond installation required.
T1059 — Command Execution
05
Kubernetes Cluster Fully Compromised
If a K8s service account token was found at the standard mount path, the payload read all secrets across every namespace and deployed privileged pods named node-setup-{node_name} to every node in kube-system, mounting the host filesystem.
T1528 — Steal App TokenT1610 — Deploy ContainerT1611 — Escape to Host

Detection Commands
# Check installed version pip show litellm | grep Version # Compromised: 1.82.7 or 1.82.8 # Find malicious .pth file find ~/.cache/uv -name "litellm_init.pth" find $(python -c "import site; print(site.getsitepackages()[0])") -name "*.pth" | xargs grep -l "subprocess" # Check for persistence ls ~/.config/sysmon/sysmon.py systemctl --user status sysmon.service # Check K8s for malicious pods kubectl get pods -n kube-system | grep node-setup # Check outbound C2 connections ss -tnp | grep -E "checkmarx.zone|litellm.cloud"
Remediation
Upgrade to LiteLLM version 1.83.0 or later using the updated CI/CD v2 pipeline
Immediately rotate all credentials on systems that previously ran versions 1.82.7 or 1.82.8
Inspect and clean the kube-system namespace by removing node-setup pods and auditing all running workloads
Remove any malicious persistence by deleting sysmon.py, disabling the sysmon service, and clearing the ~/.config/sysmon/ directory
Enforce dependency pinning and eliminate unpinned pip installations in CI/CD pipelines
Restrict GitHub Actions usage with an organization-wide allowlist and block all unverified actions

Module 1: Getting In
MITRE TA0001 — Initial Access
How attackers gain their first foothold — misconfiguration, supply chain, and application exploits.
3
Scenarios
1.1 Exposed API Server — The Unlocked Front Door Misconfiguration
▼

The K8s API server bound to 0.0.0.0 and reachable from the internet. Shodan indexes it before any attacker looks. Querying /version unauthenticated reveals the exact K8s version for targeted CVE lookup.

Reproduce (minikube)
minikube start \ --extra-config=apiserver.anonymous-auth=true # Verify — returns K8s version with no auth curl -k https://$(minikube ip):8443/version nmap -sV -p 6443,8443,10250 <target-ip>
T1190 — Exploit Public-Facing App
Detect
kubectl cluster-info ss -tlnp | grep 6443 kubectl get pod kube-apiserver-* \ -n kube-system -o yaml | grep anonymous
Fix
Bind API server to private IP — never 0.0.0.0
Set --anonymous-auth=false in kube-apiserver flags
Place behind VPN or bastion host
1.2 Malicious Container Image — Supply Chain Entry Supply Chain
▼

Pulling an unvetted image from Docker Hub that contains a known CVE or outright malicious code. Over 50% of public Docker images contain at least one critical flaw.

Scan Before You Pull
trivy image --severity HIGH,CRITICAL ubuntu:20.04 # Fail CI/CD pipeline on critical CVE trivy image --exit-code 1 --severity CRITICAL myapp:latest # Pin by digest, not tag docker inspect myimage:latest \ --format '{{.RepoDigests}}'
T1195.001 — Compromise Software Supply Chain
Fix
Use only images from trusted private registries
Pin images by digest, not tag — tags are mutable
Enforce image signing with cosign + verify at admission
Run Trivy in CI/CD — block critical CVEs before deploy
Use distroless or scratch base images
1.3 Unauthenticated kubelet Read-Only Port (10255) Misconfiguration
▼

Older clusters left kubelet's read-only port open with zero authentication. A single curl returns every running pod, environment variables, and sometimes credentials in plaintext.

Reproduce
# Zero auth — returns full pod dump curl http://<node-ip>:10255/pods nmap -p 10255 <node-ip>
T1190 — Exploit Public-Facing App
Fix
# kubelet-config.yaml readOnlyPort: 0 authentication: anonymous: enabled: false
Set --read-only-port=0 to disable entirely
Restrict port 10250 to control plane IPs only
Run kube-bench to audit kubelet config
Module 2: Breaking Out
MITRE TA0004 — Privilege Escalation + T1611 — Escape to Host
Once inside a pod, how attackers break out of the container and reach the host. These are real code-level CVEs — configuration alone cannot protect you.
3
Scenarios
2.1 runc Leaky Vessels — CVE-2024-21626 Critical
▼

A file descriptor leak in runc allows a crafted container image to access the host filesystem. Affects Docker, containerd, CRI-O, Podman.

How It Works + Detect
# Malicious Dockerfile exploits FD leak WORKDIR /proc/self/fd/<leaked-fd> runc --version # Vulnerable: < 1.1.12 docker info | grep -i runc trivy image --severity CRITICAL myimage
T1611 — Escape to HostT1068 — Exploit Vulnerability
Fix
Update runc ≥ 1.1.12 / Docker Engine ≥ 25.0.2
Use rootless containers — eliminates host UID mapping
Apply seccomp profile blocking open() on /proc/self/fd
Use gVisor (runsc) for untrusted workloads
2.2 Privileged Pod → Host Mount Escape Misconfiguration
▼

Running a pod with privileged: true and hostPID: true gives essentially root access to the host — the exact technique the LiteLLM payload used on every cluster node.

The LiteLLM Pod Spec (Lab Only)
# DO NOT run in production spec: hostPID: true containers: - name: setup image: alpine:latest securityContext: privileged: true volumeMounts: - mountPath: /host name: host-root volumes: - name: host-root hostPath: path: /
Detect + Fix
kubectl get pods -A -o json | jq \ '.items[] | select( .spec.containers[].securityContext.privileged ==true) | .metadata.name'
Enable Pod Security Admission — restricted profile
Never allow privileged: true in production
Block hostPath mounts via OPA/Gatekeeper
2.3 Linux kernel nftables Escape — CVE-2024-0193 Critical · Code Bug
▼

A use-after-free in Linux kernel nftables (< 6.6.7) exploitable from inside a container with CAP_NET_ADMIN. Root escalation on the host with no misconfiguration required.

Detection
uname -r # Vulnerable: < 6.6.7 kubectl get pods -A -o json | jq \ '.items[].spec.containers[] .securityContext.capabilities.add[]? | select(. == "NET_ADMIN")'
T1068 — Exploit for Privilege EscalationT1611 — Escape to Host
Fix
Patch kernel ≥ 6.6.7 or apply distro update (Ubuntu USN-6609)
Drop ALL capabilities — add back only what's needed
Apply seccomp profile blocking nftables syscalls
Use gVisor — intercepts syscalls before hitting the real kernel
Module 3: Taking Over
MITRE TA0008 — Lateral Movement + TA0003 — Persistence
Once on a node, how attackers escalate to cluster-admin, pivot into cloud accounts, and install persistent access that survives reboots.
3
Scenarios
3.1 nginx Annotation Injection → cluster-admin — CVE-2024-7646 Critical
▼

An attacker with CREATE Ingress permission injects malicious nginx config via annotations, leaking the ingress controller's SA token — which in default installs has cluster-admin access to all secrets.

Detect
kubectl get ingress -A -o json | jq \ '.items[].metadata.annotations | to_entries[] | select(.key | contains("snippet"))' kubectl auth can-i --list \ --as=system:serviceaccount:\ ingress-nginx:ingress-nginx
T1190 — Exploit Public AppT1528 — Steal App Token
Fix
Upgrade nginx-ingress to ≥ 1.11.2
Set --enable-annotation-validation=true
Restrict Ingress CREATE to trusted namespaces via RBAC
Remove cluster-admin from ingress controller SA
3.2 Overprivileged ServiceAccount — Pod to Cloud Misconfiguration
▼

The default SA in many clusters is over-permissioned. The LiteLLM payload read the auto-mounted SA token, enumerated all nodes, deployed pods cluster-wide, then pivoted to cloud credentials in environment variables.

Audit
kubectl auth can-i --list \ --as=system:serviceaccount:default:default kubectl get pods -A -o json | jq \ '.items[].spec.containers[].env[]? | select(.name | test("AWS|GCP|AZURE"))'
T1528 — Steal Application Access TokenT1552 — Unsecured Credentials
Fix
Set automountServiceAccountToken: false by default
Create per-workload SA with minimum required permissions
Never store cloud credentials as environment variables
Use Workload Identity (GKE/EKS/AKS) — no static credentials
3.3 Persistent systemd Backdoor via Privileged Pod Persistence
▼

The final stage of the LiteLLM attack. After escaping to the host via a privileged pod, the payload installs a systemd service beaconing to C2 every 50 minutes — surviving pod deletion and reboots.

Detection
systemctl list-units --type=service | grep sysmon ls ~/.config/sysmon/ kubectl get pods -A | grep node-setup ss -tnp | grep -E \ "checkmarx.zone|litellm.cloud" falco -r /etc/falco/falco_rules.yaml \ -o json_output=true | grep systemd
T1543 — Create or Modify System ProcessTA0003 — Persistence
Fix
Remove sysmon.py — disable and delete sysmon.service
Block egress from nodes to unknown IPs via NetworkPolicy
Use Falco rules to alert on new systemd service creation from containers
Implement node immutability — read-only root filesystem

The Supply Chain Golden Rules — 2026 Edition
Pin every dependency by exact version + hash — never use unpinned pip install
Treat your CI/CD pipeline as part of your attack surface
Rotate credentials immediately if any tool in your pipeline is compromised
Subscribe to security advisories for every tool in your stack
Assume any system that installed a compromised package is fully compromised
